# BHEX Runtime Inventory

## Purpose

This inventory establishes the BHEX repository population used as the discovery source for the Distributed Relay Framework (DRF) constitutional convergence assignment.

The manager instruction supplied for this assignment is:

> "Document the ones in BHEX."

Therefore, the BHEX Engineering Exchange repository population is treated as the discovery source.

A repository is not automatically treated as a runtime participant merely because it exists in BHEX. Constitutional identity is assigned only where repository evidence supports an operational, integration, registry, execution, replay, evidence, observability, or knowledge responsibility.

---

## Classification Rules

### Yes — Runtime Participant

Repository evidence demonstrates an operational runtime responsibility.

### Yes — Supporting Runtime Participant

Repository evidence demonstrates participation in runtime integration, operational visibility, persistence, evidence, replay, provenance, registry, or supporting infrastructure without assigning primary execution authority.

### Candidate

The repository appears relevant by purpose, structure, or naming, but the available evidence is insufficient to assign permanent constitutional authority.

### Unresolved

Insufficient repository evidence is available to determine constitutional participation.

### Excluded

The repository is not used as constitutional evidence because the required implementation evidence is unavailable, inaccessible, or outside the assignment evidence boundary.

# Constitutional Identity Boundary

The following rule applies throughout the DRF documentation:

> Repository existence does not imply constitutional authority.

A repository may be:

- a runtime participant,
- a supporting runtime participant,
- a registry participant,
- a capability participant,
- a knowledge participant,
- a candidate,
- unresolved,
- or excluded.

No constitutional authority is assigned without repository evidence.

---

# Important Authority Boundaries

The current evidence supports the following non-overlap principles:

### SVACS Unified Core

Owns runtime execution-chain responsibilities demonstrated by the repository.

It does **not** automatically own:

- Capability Registry authority
- Governance authority
- Knowledge authority
- Review authority
- Repository Registry authority

unless independently evidenced.

### Capability Registry Foundation

Owns capability/module registration and metadata management.

It does **not** own:

- Runtime execution
- Runtime orchestration
- Governance decisions
- Replay execution

The repository explicitly describes itself as not implementing AI, orchestration or runtime execution.

### BHIV Bucket

Owns artifact persistence and integrity mechanisms demonstrated by the repository.

It does **not** own:

- Business execution decisions
- Governance decisions
- Capability lifecycle decisions
- Runtime orchestration

### SHAKTI

Owns operational visibility and command-center presentation/integration surfaces.

It does **not** become the authority for the backend runtime services it observes.

### Canonical Capability Convergence

Owns reusable capability composition and capability integration patterns evidenced by the repository.

It does **not** automatically become the execution authority for every capability it coordinates.

---

# Evidence Boundary

This inventory intentionally does not invent runtime participants, ownership, APIs, events, SDK interfaces, authentication schemes, schemas, or authorities for repositories whose implementation/documentation has not been sufficiently inspected.

Unresolved repositories remain explicitly marked as unresolved.

This prevents DRF from creating false constitutional authority through assumption.
